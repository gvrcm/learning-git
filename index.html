01

Repository (repo)

git init · then host it on GitHub

What it does

A repository is the project folder Git is tracking. Locally it is a directory plus a hidden .git database of history. Remotely it is that same project hosted on GitHub, GitLab, or similar, so other people can clone, review, and contribute.

Considerations

  • Add a .gitignore before the first commit so secrets, node_modules, and build output never enter history.
  • One repo, one product. Avoid dumping unrelated projects into the same history.
  • README, license, and a clear default branch (main) make the repo usable the moment someone lands on it.

Resources

  • Pro Git: Getting a Git repository
  • GitHub: About repositories
  • git-scm: gitignore

02

Clone

git clone git@github.com:org/repo.git

What it does

Clone downloads a full copy of a hosted repository onto your machine: the files at HEAD, the commit history, and a remote named origin pointing back at the host. After a clone you can branch, commit, and (if you have access) push.

Considerations

  • Prefer SSH keys for frequent work; HTTPS is fine for a one-off download.
  • Cloning a fork is different from cloning the upstream repo. Know which remote you will push to.
  • Huge histories can use --depth 1 for a shallow clone, but you will lack older commits until you deepen it.

Resources

  • git-scm: git clone
  • GitHub: Cloning a repository
  • GitHub: SSH authentication

03

Branch

git switch -c feature/hero

What it does

A branch is a movable pointer to a commit, which gives you a safe parallel timeline. Work on the branch without touching main until you intentionally combine them. GitHub uses branches as the unit of a pull request.

Considerations

  • Keep branches short-lived. The longer they drift from main, the harder they are to merge.
  • Name them after the work (fix/nav-overlap, feat/dark-mode), not after yourself.
  • Do not commit directly to main on a shared repo. Branch first, even for a one-line change.

Resources

  • Pro Git: Branches in a nutshell
  • GitHub: About branches
  • GitHub Flow

04

Commit

git add -p && git commit -m "Fix hero contrast"

What it does

A commit is a snapshot of the project plus a message describing why it changed. Git stores a pointer to the tree of files, the parent commit, the author, and the time. History is a chain of these snapshots.

Considerations

  • Make commits small and reviewable: one idea per snapshot.
  • Write the message for a future teammate (including you). Say why, not only what.
  • Stage with intent. git add . is easy to over-commit with; git add -p lets you choose hunks.

Resources

  • git-scm: git commit
  • Chris Beams: How to write a git commit message
  • Conventional Commits

05

Push / Pull

git push -u origin HEAD · git pull

What it does

Push uploads your local commits to the hosted repository. Pull downloads new commits from the host and updates your current branch (fetch + integrate). Together they keep local and remote in sync.

Considerations

  • Pull before you push if others work on the same branch, or you will be asked to integrate first.
  • Never git push --force to main. Force-with-lease is safer, and still reserved for branches you own.
  • git fetch is pull without merging. Use it when you want to inspect incoming work first.

Resources

  • git-scm: git push
  • git-scm: git pull
  • GitHub: Pushing commits

06

Diff

git diff main...HEAD

What it does

A diff is the visual difference between two versions of the code. Git can compare working files to the index, the index to the last commit, or any two commits or branches. On GitHub, the Files changed tab of a pull request is a diff.

Considerations

  • Read your own diff before you commit. It is the cheapest review you will get.
  • Three-dot diffs (main...branch) show what the branch introduced since it diverged. Two-dot diffs compare tips directly.
  • Whitespace-only noise can hide a real change. Use ignore-space options when the design tokens reflow.

Resources

  • git-scm: git diff
  • GitHub: Comparing commits
  • GitHub: Comparing branches in PRs

07

Merge

git switch main && git merge feature/hero

What it does

Merge combines a branch back into another branch. Git finds a common ancestor and, if the changes do not collide, creates a new merge commit with two parents (or fast-forwards if nothing happened on the target).

Considerations

  • A merge commit preserves the true parallel history. Squash merge on GitHub collapses the branch into one commit on main.
  • Merge main into your feature branch often so the final merge stays small.
  • If Git cannot combine both sides, you get a merge conflict instead of a clean merge.

Resources

  • git-scm: git merge
  • Pro Git: Basic branching and merging
  • GitHub: About pull request merges

08

Rebase

git fetch origin && git rebase origin/main

What it does

Rebase replays your commits on top of the latest main. Git peels your commits off, moves the base to the new tip, and reapplies each patch in order. The result is a linear history as if you had started from today’s main.

Considerations

  • Do not rebase commits that other people already pulled. Rewriting shared history forces everyone else to recover.
  • Rebase feature branches you own to stay current. Prefer merge for public, long-lived branches.
  • Conflicts still happen, but you resolve them commit-by-commit instead of all at once.

Resources

  • Pro Git: Rebasing
  • Atlassian: Merging vs. rebasing
  • git-scm: git rebase

09

Merge conflict

markers: <<<<<<< ======= >>>>>>>

What it does

A merge conflict means two changes touched the same lines (or one side edited a file the other deleted). Git stops and asks you to choose. You edit the file, remove the markers, then git add and continue the merge or rebase.

Considerations

  • Read both sides. The goal is the intended design, not “whoever committed last.”
  • Talk to the other author when the conflict is conceptual (two different button patterns, not two colors).
  • After resolving, run the app. A conflict-free file can still be a broken layout.

Resources

  • GitHub: About merge conflicts
  • git-scm: How to resolve conflicts
  • Resolve a conflict on GitHub

10

Pull Request (PR)

GitHub: “please review and merge my branch”

What it does

A pull request is a conversation around a branch: the diff, checks, review comments, and the eventual merge into the target branch. It is the social layer on top of push, diff, and merge.

Considerations

  • Keep PRs small enough to review in one sitting. Screenshots help for visual work.
  • Describe the why, link the issue, and say how you tested. Reviewers should not have to reverse-engineer intent.
  • Do not merge your own PR on a team without a look from someone else, unless the repo explicitly allows it.

Resources

  • GitHub: About pull requests
  • GitHub: Pull request reviews
  • GOV.UK Design System: Pull requests

11

Issue

a ticket: bug, feature, or task

What it does

An issue is a tracked piece of work on GitHub: a bug, a feature, a design question, or a chore. It holds context, discussion, labels, and later a link to the pull request that closes it. Git stores history; issues store intent.

Considerations

  • Write a reproduction or a success condition. “Button looks wrong” is not enough; say where, in which viewport, and what “right” is.
  • One issue, one outcome. Split “redesign the dashboard” into reviewable tickets.
  • Link the PR with Closes #12 so the issue archives itself when the work merges.

Resources

  • GitHub: About issues
  • Linking a pull request to an issue
  • Issue templates
